
## 2026-05-18 - String Lowercasing in Search Hot Loops
**Learning:** Repetitive string operations like `.lower()` inside `for term in terms` and per-row `for row in rows` iterations (in `search_query.py`, `store.py`, `dag.py`) create severe CPU bottlenecks for large queries and results. Python strings are immutable, so `.lower()` allocates memory and processes the entire string from scratch on every invocation. Calling `.lower()` inside `count_term_matches` effectively caused \(O(N_{rows} \times M_{terms})\) lowercasing operations on potentially large message contents or summaries.
**Action:** When implementing custom scoring or search metrics in Python, pre-compute case-normalization outside of nested loops. Modify core shared utilities (like `count_term_matches`) to accept pre-lowered strings via a flag (e.g. `is_lowered=True`) rather than blindly normalizing inputs. Pre-compute `lowered_terms = [t.lower() for t in terms]` once per function call, and `lowered_content = content.lower()` once per candidate row, minimizing memory allocation and dramatically speeding up the overall fallback scoring pass.
